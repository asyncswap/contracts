Async Swap protocol

Async Swap is a Uniswap v4 hook that turns exact-input swaps into resting limit orders. The hook uses v4 custom accounting (beforeSwapReturnDelta) to take the whole swap input as an order, and v4 flash accounting (one PoolManager.unlock per action, every delta zero at the end) to settle matches, fills and fees. Orders are good till cancelled (GTC): there is no expiry, so an order rests until it fills or the maker cancels it.

This page is the entry point. It shows the contracts, where funds sit, how an order is placed, and who may do what. Every box names a contract, library or function in src/, so the diagrams can be checked against the code.

1. Components

Loading diagram...

Anyone may open a pool on the hook with the dynamic-fee flag. A pool that holds the chain's USDC (numeraire) opens freely. A pool without it, such as ETH/TOKEN, opens once both tokens already have a numeraire pool on this hook with the same tick spacing; see non-numeraire pools.

Each order must meet two floors, fixed when the pool opens:

  • Minimum order on the quote leg: USDC on a numeraire pool, from the constructor's whole-dollar minimum scaled by decimals().
  • Asset floor on the other leg: 10^(decimals - assetPrecision) base units (0.0001 token with the deployed precision of 4). Native ETH counts as 18 decimals; an asset with no code is rejected.

No check reads a price, and nothing has a setter, so the owner cannot change the rules under live orders. beforeAddLiquidity is a pass-through: ordinary v4 range positions are the inventory for pool fills. No user swap reaches the AMM curve directly, because beforeSwap takes the whole input as an order. The standalone MatchingEngine.sol is a benchmark harness and is not deployed.

calculatePoolFee and calculateHookFee are zero. A maker's guarantee is its minimum output minus 0.02%. Refunds and cancels are not charged. See dynamic fee ordering for the pool-fill fee.

MEV tax. The Router charges mevTax() on swap, swapWithSig, fillOrder and fillFromPoolLiquidity, and on every flash fill (the outer fill and each nested fillOrderInCallback). On a chain that orders transactions by priority fee, searchers racing for one position bid that fee up, and the tax turns most of the bid into protocol revenue. A transaction with no priority fee pays nothing. Plain actions pay it in msg.value; flash fills pay it in flash-accounting style, see paying the MEV tax. Cancels, claims, top-ups and matchBook are not taxed. A searcher can still race untaxed by repricing its own order and settling it with matchBook; no user loses funds that way, the protocol only collects less (acknowledged in the 2026-11-01 Pashov review, findings 4, 5, 6 and 9).

Invariant. The hook's claim balance per currency equals the remaining input of open orders plus escrowed bids, fuzzed by the matching invariant suites. The hook's own token balance is zero between transactions, so sweep only moves funds sent to the hook by mistake.

3. Placing an order

Loading diagram...

Signed orders follow the same path through swapWithSig: one Permit2 PermitWitnessTransferFrom whose witness is OrderSignatures.hashOrder(order), plus an optional signed SetExecutor grant. An order's id is keccak(chainId, poolId, owner, zeroForOne, salt); the hook assigns the salt and emits it in AsyncOrderCreated.

The new order goes to the better venue first. If the pool has active liquidity and its spot price is strictly better than the best opposing level, the pool fills up to that level and the book takes the rest. Otherwise the book matches first and the pool must take the whole remainder or roll back. See the lifecycle for everything after placement.

4. Authorization

Loading diagram...

Router.multicall runs several Router calls atomically as the caller. It is not payable, so native-value actions are sent on their own. The Router can never be revoked as an executor (CannotRevokeTrustedRouter), so a maker's orders are never trapped. Signed maker actions use unordered nonces in AsyncSwap.nonceUsed; invalidateNonce revokes any of them.

5. Modules and libraries

Measured with solc, the hook and Router sit near the EIP-170 limit, so most logic runs in linked libraries and one Router module. Public library functions run by DELEGATECALL in the hook's context, so escrow, books and transient records stay in the hook.

Loading diagram...

RouterFlashFills called directly reaches the hook as itself, not as the Router, and flashFill refuses it (NotTrustedRouter). Its code counts toward the Router's initcode, not its runtime.
