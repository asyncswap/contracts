# formal/: Lean proofs for the Async Swap contracts

Lean 4 (`leanprover/lean4:v4.35.0`) + Mathlib specification and machine-checked proofs of `src/`,
ported from [asyncswap/v2-proofs](https://github.com/asyncswap/v2-proofs) (`dev` @ `f3c37e4`), plus
the link from those proofs to the code.

| Library | What it is |
| --- | --- |
| `AsyncSwapSpec` | v2 hook: protocol fee, order matching, partial fills, escrow invariant, admin, `RadixPriceTree` ([README.spec.md](README.spec.md)) |
| `AsyncSwapProtocol` | Call-sequence state machine: Router → PoolManager → hook → FeeVault, token ledgers, claims, deltas. `V2/` adds priority bids, matching, liquidity fills and NativeClaims, with escrow, balance, claims, backing, conservation and supply invariants over every entry point (`step_*`) |
| `Generated` | The Lean model of `Router` and `AsyncSwap`, generated by Formal Mind's `formal-ast` from solc's AST (`scripts/generate.sh`). Don't edit: regenerate |
| `Refinement` | Theorems tying each generated def the Foundry scripts call to the `AsyncSwapProtocol.V2` operation it implements |

```sh
cd formal
lake exe cache get   # Mathlib build cache
lake build           # every theorem; no sorry, no extra axioms
```

Each file in `Generated/` carries its own copy of formal-ast's `FormalAst` prelude, so the two are
built as separate modules and never imported together.

## How the proofs reach the code

The spec theorems are about abstract models (`World`, `step`), not the contracts. `Refinement/`
proves, for each function the scripts under `script/` call, that the generated def implements the
spec's step, so the spec's invariants apply to the code. Formal Mind's Audit page counts a function
as proved when a theorem in this folder names its generated def.

| Function (script) | Refinement theorems | Spec it connects to |
| --- | --- | --- |
| `AsyncSwap.setExecutor` (`Trade.s.sol`) | `setExecutor_run`, `setExecutor_refines`, `setExecutor_frame`; invariants `setExecutor_escrow`, `_bal_nonneg`, `_claims_nonneg`, `_backing`, `_conservation`, `_reserves_nonneg` | `Protocol.setExecutor` / `step (.setExecutor …)`; `step_escrow`, `step_bal_nonneg`, `step_claims_nonneg`, `step_backing`, `step_conservation`, `step_reserves_nonneg` |
| `AsyncSwap.isExecutor` (`Trade.s.sol`) | `isExecutor_refines` | `World.isExecutor`, read by `createHookGuard`, `fillGuard`, `cancelHookGuard` |
| `Router.swap` (`03_Swap.s.sol`, `Trade.s.sol`) | `swap_sound`, `swap_complete`, `swapGuard_router`, `userParamsOf_abiEncode` | the Router's conjuncts of `swapGuard` (owner = caller, `UserParams`, `msg.value`), then `unlock(SwapCallback(Swap, order))` |
| `Router.cancelOrder` (`04_CancelOrder.s.sol`) | `cancelOrder_sound`, `cancelOrder_complete`, `spec_cancelOrder_owner`, `unlockCallback_cancel` | `cancelOrder`'s `sender = o.owner`; the callback becomes `HOOK.cancelOrder(order)` with the same order |
| `Router.fillOrder` (`05_ExecuteOrder.s.sol`) | `fillOrder_maxPrice` (via `unlockCallback_fill_maxPrice`) | `fillGuard`'s `liveGross ≤ maxPrice` |

What "refines" means here, per def: **sound** (a run that does not revert satisfies the spec
guard's conjuncts this contract checks) and **complete** (when they hold, the def does exactly the
spec's step: its storage writes and the call it hands on, with the same order). `setExecutor` is
refined in full: it is the spec step, so every `step_*` invariant carries over. For the Router the
spec operation spans several contracts; the theorems cover the Router's part.

Standing assumptions, stated as hypotheses: `ext.get (ext.set w s) = s` (the world gives a contract
back the storage it wrote); `Binds` (the spec `Config` is this Router and this pool: `currency0` is
native iff it is `address(0)`, the numeraire `currency1` is not); `Encodable` (the order's fields fit
their ABI types, which any calldata order does).

## Gaps

- **`Router.fillOrder` is opaque in the generated model.** Its body sends ETH with
  `address(HOOK).call{value: msg.value}("")`, which formal-ast does not translate yet. Its theorem is
  conditional: `FillOrderReachesCallback` states, as a hypothesis, what the body and
  `PoolManager.unlock` do. The FillOrder callback itself (`unlockCallback_fill_maxPrice`) is proved
  against the generated code. The `msg.value == livePrice` check for native output is not covered.
- **Cross-contract composition.** `Router.swap` / `cancelOrder` end at `PoolManager.unlock` and the
  callback ends at `HOOK.*`; the PoolManager and the hook are `Ext` calls in the Router model. The
  hook's half of `swapGuard`, `cancelHookGuard` and `fillGuard` (executor approval, open order,
  escrowed bid, balances) and the bodies `swapBody`, `cancelBody`, `fillBody` are not yet refined against
  `Generated/AsyncSwap.lean`. A full refinement needs an abstraction from the hook's storage
  (`asyncOrders`, `priceBooks`) to `World.orders` / `openKeys`. Several hook functions are opaque in the
  model (`_createOrder`, `AsyncFiller._append` / `_remove` / `level`, `CurrencySettler.settle`).
- **Token movements.** `_settlePriorityFee`, `_settleWithPermit`, `CurrencySettler.settle`,
  `CurrencyLibrary.transfer` are opaque, so the spec's ledger effects (`bal`, `claims`, deltas) are not
  yet tied to code.
- **Routing of Swap / Match / LiquidityFill callbacks** (actions 0, 4, 5) is not proved; Cancel (2)
  and FillOrder (1) are.
- **Not called by any script, not linked:** `swapWithSig`, `cancelWithSig`, `matchBook`,
  `fillFromPoolLiquidity`, `AsyncSwap.setExecutorWithSig`, ownership and nonce admin.
