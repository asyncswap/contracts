Async Swap v2 protocol map

Async Swap v2 is a Uniswap v4 hook that turns exact-input swaps into resting limit orders. This page describes the whole protocol in diagrams: which contracts exist, where funds sit, how an order is created, matched, filled, repriced and cancelled, and who is allowed to do what. Every box names a contract, library or function in src/, so the diagrams can be checked against the code.

1. Components

Loading diagram...

Every pool that uses the hook must contain the chain's USDC (numeraire) and use the dynamic-fee flag (beforeInitialize). beforeAddLiquidity is a pass-through: anyone may add ordinary v4 range positions, and they are the inventory for the LP-fill path. No swap ever reaches the AMM curve directly, because beforeSwap consumes the whole input as an order; the only AMM swaps are the ones the hook itself performs when it fills a resting order from pool liquidity. The standalone MatchingEngine.sol is a benchmark harness and is not deployed.

FeeVault owns claims recorded in PoolManager. Crediting those claims does not call FeeVault.

2. Where funds live

Loading diagram...

Fees, by path: an order-to-order match charges nothing; a filler fill (Router.fillOrder) pays the maker's live minimum plus 30 bps of gross output, and that fee lands in the FeeVault as claims; an LP fill charges the 30 bps dynamic LP fee to the active v4 positions. calculateHookFee is zero. Priority bids are escrowed as hook claims by addOrder and settle to the FeeVault: the filled share as input fills, the rest when the order closes. They never go to LPs, so liquidity added just before a settlement earns none of them.

An order-to-order match pays both sides, and returns any remainder left below the pool minimum, as PoolManager claims rather than token transfers, so a recipient a token refuses cannot block matching. Holders redeem ERC-20 claims through TokenClaims and native claims through NativeClaims, to any recipient, after approving the redeemer for that claim id. Filler fills and LP fills pay the maker's ERC-20 output directly. Minting bid claims creates hook debt immediately; the PoolManager unlock must settle that debt, including for custom executors. The Router pays it with settleFor(hook). All pools rank equal prices by remaining bid, then sequence. There is no FIFO mode or mode switch.

The accounting invariant is fuzzed by the matching invariant suites: the hook's claim balance for each currency equals the sum of remaining inputs of open orders plus escrowed bids, and nothing is created or destroyed by a match. The hook's own token balance is zero between transactions, so sweep can only move stranded ETH or tokens sent to the hook by mistake, never escrow.

3. Placing an order

Loading diagram...

Signed orders follow the same path through swapWithSig. The maker signs one Permit2 PermitWitnessTransferFrom whose witness is OrderSignatures.hashOrder(order), so the signature both moves the input and commits to the order. A relayer can also attach a signed SetExecutor grant for the maker's first order on a pool.

4. Everything after placement

Filler fills, book continuation, LP retries, repricing, cancellation, pool setup, native-claim redemption and fee collection are drawn step by step in contract-call-sequences.md; the lifecycle and priority-bid flowcharts are in order-lifecycle.md. Three facts to keep in mind while reading them:

  • An order-to-order match charges no fee. The 30 bps protocol fee is paid by the filler on top of the maker's live minimum and is credited to the FeeVault as ERC-6909 claims inside the PoolManager; the LP-fill path instead charges the 30 bps dynamic LP fee to active v4 positions. calculateHookFee is zero.
  • updatePrice only re-ranks the order in the book. It needs no PoolManager unlock and triggers no matching; a later crossing order, matchBook, a filler or an LP retry has to execute it.
  • matchNewOrder is gated by a transient slot that beforeSwap writes for the current transaction. executeOrder, cancelOrder and tryFillOrderFromPoolLiquidity check isExecutor[maker][caller] instead.

An order's identity is keccak(chainId, poolId, owner, zeroForOne, salt). The hook assigns the salt at creation and emits it in AsyncOrderCreated; later calls recompute the id from the maker's struct, so a maker needs the event or an indexer to cancel or reprice.

5. Authorization

Loading diagram...

Signed maker actions use unordered nonces: AsyncSwap.nonceUsed for SetExecutor and UpdatePrice, Router.cancelNonceUsed for CancelOrder, and Permit2's own nonces for order witnesses. The Permit2 witness binds maker, both tokens, amounts, bid and pool; it leaves out sqrtPrice (never read, the hook consumes the whole swap) and salt (assigned by the hook).

6. Deployment shape

Loading diagram...

script/deploy.sh <chain-key> [dry-run|broadcast|verify] runs this sequence against script/config/chains.json. On chains whose gas token has an ERC-20 twin (Arc: native USDC and 0x3600…0000 are one balance) never initialize a native-currency pool; pair the ERC-20 USDC with a normal ERC-20 asset.

See also price-key-crossing.md for how truncated price keys decide whether two orders cross, and mainnet readiness for the release gate.
