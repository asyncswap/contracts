Audit scope: Async Swap (2026-11-05)

Supersedes the 2026-11-03 scope, which froze protocol code at 2739d6c. The prior findings and their dispositions are carried forward below; passing tests are validation evidence, not a new security audit.

  • Repository: asyncswap/contracts
  • Protocol and production deployment code frozen at: c9372ff9577ba3950fa321090a7bfb559fc964a4 on main. This includes the bitmap optimization (#77) and funded fee top-ups (#78). Check out this exact commit for the protocol review. Later release evidence and integration work do not change this frozen source.
  • Compiler: solc 0.8.26, optimizer on (optimizer_runs = 10_000); see foundry.toml.
  • Chain: Unichain (130) first; any EVM chain with Uniswap v4 later.
  • Builds on: Uniswap v4 PoolManager (hooks, ERC-6909 claims, dynamic LP fee), Permit2 for signed orders, OpenZeppelin SafeERC20, EIP712, SignatureChecker and Multicall.

Changes since the last freeze (2739d6c)

  • Bounded outer tick bitmap. TickBitmap replaces the outer radix price index in AsyncFiller.Book; the inner Patricia priority tree remains. Check tick boundaries, empty levels, best-price selection and count consistency. This changes storage layout and requires a new deployment; no in-place migration exists.
  • Linked exact-price updates. EligiblePrice.refresh/remove are now public linked-library calls to keep matching bytecode deployable. Verify caller storage layout, link addresses and summary repair.
  • Funded fee top-ups. Router.topUpPriorityFee(order, addedFee) authenticates the maker, transfers the delta in the numeraire and credits the hook before PriorityFeeUpdates rekeys the inner queue and mints claims. The resulting remaining bid must meet the current minimum and fit uint64. Only the trusted Router can enter the hook endpoint. Price, input budget, original maker age and signed-reprice version stay intact; fee-tier FIFO age resets. Top-ups are non-refundable, untaxed by the Router's native MEV tax and do not invoke matching. Makers can batch a bounded matching call with multicall.
  • Payment callbacks and signatures. The amendment reads live state after payment. A partial fill during payment changes the remainder to which the delta is added; closure reverts the entire transaction. Existing signed reprices and cancellations remain valid unless their own validity conditions change.
  • Deployment links. Production and local deployment wrappers now link TickBitmap, EligiblePrice, and PriorityFeeUpdates, in dependency order. A supplied matcher override must match this build's predicted address; having code alone is insufficient.
  • Validation. Independent linear-scan matching-model tests, bitmap boundary/property tests, funding and callback regressions, mixed top-up invariants, and public-Router gas measurements accompany the changes.

What it is

Async Swap is a Uniswap v4 hook that turns swaps into limit orders. Makers escrow their input in the hook and set a minimum output. Every pool pairs an asset with USDC (the numeraire). Orders are filled by matching against each other, by permissionless fillers, or against the pool's own liquidity.

  • Pools. Anyone can create a pool: the hook accepts one that pairs the configured USDC with an asset that has code and uses the dynamic-fee flag. The owner cannot open, close or configure pools.
  • Book. Orders sit at price levels on v4 ticks (TickPrice: the floor tick of the exact limit, 0.01% apart). The outer index is a bounded bitmap. Within a level they rank by exact limit, then escrowed priority bid, then arrival (EligiblePrice); exact rational limits decide crossing. New orders and any crossed backlog share one book-wide selection, at most eight pairs per call.
  • Venue choice. A new order goes to the better venue first (TickPrice.poolBeatsLevel). If the pool's price beats the best opposite level (inside the dynamic-fee window, counting the fee a fill back toward the reference would pay), the pool goes first, limited one tick short of that level and inside v4's price range, and the book matches the rest. Otherwise the book goes first and the pool must take all of any remainder. A pool fill that would leave no active liquidity reverts.
  • Fees. Book matches and filler fills take 0.02% from what each side receives. Pool fills pay active LPs 0.02% and the protocol 0.01%, plus a dynamic fee (DynamicFeeOrdering) on a fill that moves the price back toward the first pool fill's starting tick within 2 blocks: half the gap it closes, half to LPs and half to FeeVault.
  • Settlement. Book matches credit both sides, and any remainder left below the pool minimum, as PoolManager ERC-6909 claims, batched per call (ClaimTransfers). Holders redeem them through TokenClaims (ERC-20), NativeClaims (ETH) or Router.withdrawClaims. Filler fills and full pool fills pay ERC-20 output directly; native output, and a pool fill that leaves part of the order on the book, are credited as claims.
  • Priority bids. Optional, paid in USDC and escrowed when the order is created. Each fill settles its proportional share and the rest settles when the order closes. Every settled bid goes to FeeVault, never to LPs. Makers may add funded USDC to the remaining bid through the Router; this changes fee priority without changing their limit price.
  • Minimums. Fixed at deployment, no setter: an optional minimum order in USDC (minOrder, from a dollar amount and the numeraire's decimals; 0 by default) and an asset floor per pool (minAssetAmount, 10^(decimals − 4), so 0.0001 of a token). The $0.10 bid cap is derived from the numeraire's decimals too.
  • Signed actions. Permit2 order witnesses (swapWithSig), SetExecutor, UpdatePrice (binds the order's createdSequence and its reprices count; a reprice that lands after partial matches applies its signed price to the remainder) and CancelOrder (no order size: covers whatever remains). All use unordered nonces in one space.
  • Router. The single trusted entry for order creation, and an executor makers can't revoke. multicall batches actions as the caller (not payable). Order creation and fills pay an MEV tax of the transaction's priority fee times MEV_TAX_GAS (per chain, fixed at deployment: 20,000,000 on Unichain and Unichain Sepolia, which order by priority fee), in msg.value on top of any native deposit, credited to FeeVault as native claims. The Router can cancel for a maker without an executor grant.

Trust assumptions

  • Owner (two-step transferOwnership / acceptOwnership): sweeps tokens sent to the hook by mistake (sweep; escrow lives in PoolManager claims, not the hook's balance) and collects fees, bids and MEV tax from FeeVault. It cannot open, close or configure pools or change minimums. Must not be able to take makers' escrow.
  • Router: the hook trusts its immutable router as the only order-creation path, as an executor no maker can revoke, for grant-free cancels on a maker's behalf (the Router checks the owner or a signature), and for burning cancel nonces, and for maker-authorized, funded priority-fee amendments. A generic executor grant does not authorize spending a maker's USDC for top-ups.
  • Executors: a maker authorizes executors per pool (setExecutor or setExecutorWithSig) and can revoke any of them except the Router. An executor can only act on that maker's orders.
  • Fillers / matchers / keepers: anyone; permissionless.
  • Pool creators: anyone, for any asset with code. A malicious asset must only be able to affect its own pool.
  • Tokens: USDC plus standard ERC-20s and native ETH. Fee-on-transfer and rebasing tokens are not supported.

Known issues (do not report)

Acknowledged in the reviews below:

  • Ways to race without the MEV tax (Pashov 4, 5, 6, 9): a searcher can reprice its own resting order with updatePrice and settle it with matchBook (on the Router or directly on the hook, which needs no unlock), or pool-fill its own order through tryFillOrderFromPoolLiquidity with its own contract as executor. No user loses funds; the tax covers Router creation and fills only.
  • A partly matched order can fall behind an equal-priced order (Pashov 7): the remainder's minimum rounds up, so its exact limit is one unit worse than the maker signed and its bid buys no priority. Pinned by test_knownIssue_partlyMatchedOrderFallsBehindAnEqualOrder.
  • Fees round to zero on dust orders (LSP I-01): only with minimums off.
  • The MEV tax needs an exact msg.value: the deposit plus priority fee × MEV_TAX_GAS. Wallets should send taxed calls with no priority fee; the app does.

By design:

  • A top-up is an additive action. Repeating it in a new transaction spends the delta again. It resets fee-tier age, not maker age, and does not invalidate a previously signed cancellation or reprice. A multicall can commit a top-up even when matching succeeds with zero fills. These are explicit semantics, not fill guarantees.

  • Makers can't revoke the Router. A maker who wants out cancels its orders (through the Router, by signature, or directly from its own unlock); the Router acts for a maker only when that maker calls it or signs.

  • Priority bids and top-ups are non-refundable. All of a bid goes to FeeVault, including on cancellation or a dust close.

  • Tokens with recipient callbacks (e.g. ERC-777) are not supported. Matching pays only claims and runs no recipient code; filler fills and full pool fills transfer ERC-20 output after the order is closed.

  • Proceeds are claims. Recipients redeem through TokenClaims, NativeClaims or Router.withdrawClaims.

  • DeployWithdrawalRouter deploys a testnet-only second Router for claims; the hook trusts only its own Router, so cancels through the second one fail.

  • MatchingEngine.sol is a benchmark harness, not deployed (AuditAgent finding 8, acknowledged).

  • Release items in MAINNET_READINESS.md (deployment rehearsal, bytecode pinning, throughput stress, deploying the claim redeemers) are operational, not code findings.

The 29 leads in the Pashov review and the leads in the LSP review are unconfirmed trails, not known issues: confirming or ruling out any of them is in scope.

Testing

At the freeze commit (PR #78 validation):

  • forge test: 1,024 passing, 0 failing, 0 skipped, 184 suites, including the three pinned Unichain fork tests at block 61,709,000. Default solc 0.8.26; optimizer 10,000 runs. PR CI also passed with pinned Foundry 1.8.6.
  • Invariants retain 64 runs × depth 64 with fail-on-revert. Handlers now interleave fee top-ups with submission, cancellation, repricing, matching, claim redemption and LP fills. They check escrow obligations, conservation and best exact-price/fee/age selection.
  • MatchingReference.t.sol independently scans orders and calculates settlement. Fuzz campaigns use 256 runs of 64 mixed operations, plus deterministic backlog, maker-age and dust-closure cases. The model shares TickPrice only for the documented age reset when rounding moves an order to another tick.
  • PriorityFeeTopUp.t.sol covers ownership, funding failure/short payment, zero/max bids, minimum admission, partial fills, both numeraire positions, configured decimals, multicall rollback and payment callbacks. SignedOrders.t.sol checks pending signed reprices and cancellations after top-ups.
  • The old freeze's coverage percentages have not been rerun for this source and are not current coverage claims. The formal fixtures are executable bytecode checks; legacy Lean models are not maintained proofs of this release.
  • Runtime sizes (limit 24,576 bytes): hook 24,159; matcher 24,225; Router 23,061; fee-amendment library 5,537; bitmap 696; exact-price library 1,966. Hook/matcher headroom is 417/351 bytes.
  • Bitmap measurements compare the prior radix book with the optimized book before top-ups. Top-up measurements use actual Router receipts: 186,710–235,267 gas over four fixtures, including intrinsic gas and refunds, excluding approvals/setup. Neither is a production-throughput guarantee.
